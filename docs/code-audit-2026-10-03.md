# Website code audit — 2026-10-03

**Scope:** the React/Vite interface, shared Zod contracts, Fastify routes and modules, Prisma ownership boundary, data/cache adapters, request logging, and repository security/configuration. The [website guide](website-guide.md) maps each view to the logic and data that powers it. This report records local code and test evidence; it does not certify GitHub settings, production HTTP headers, or the mini-PC host.

## Result

The site has a compact Generation 9 scope and its primary game calculations use pinned local `@smogon/calc` data. The audit found mismatches in account state, input-dependent results, browser storage, API error handling, response contracts, the Pokédex's sprite/cache path, and bodyless team deletion. The targeted fixes below preserve the approved stack and product scope.

The review applied the repository's [`react-best-practices` skill](../.agents/skills/react-best-practices/SKILL.md), including local-storage versioning and effect cancellation; [`fastify-best-practices`](../.agents/skills/fastify-best-practices/SKILL.md), including route schemas, errors, and testing; and [`security-best-practices`](../.agents/skills/security-best-practices/SKILL.md), using its React web reference for the client and the project security plan for Fastify. The findings were reproduced with Testing Library, unit tests, Fastify injection, and a local disposable-PostgreSQL browser journey. No production host, credentials, or private course sources were used.

The React guidance applies to AUD-01 and AUD-07–10: asynchronous work is tied to the current session or inputs, persisted edits have an explicit version and recoverable shape, and form state is not collapsed while the user is editing. The Fastify guidance applies to AUD-04, AUD-06, and AUD-14: routes declare the responses they own, status codes stay meaningful, unexpected failures are handled at the server boundary, and tests wait for the services they depend on. The security guidance applies to AUD-02, AUD-03, and AUD-05: cookie-authenticated mutations check their source, logs avoid credentials, and remote image URLs and CSP permissions are narrowly constrained. These are code-quality recommendations applied in this project; they do not certify the deployed host.

## Findings and fixes

| ID | Priority | Problem and user/security impact | Fix and verification |
| --- | --- | --- | --- |
| AUD-01 | High | After logout, a library already loaded in the React `saved` array remained available on the builder screen. A slow list response could also return after the user changed. | Logout/session refresh immediately invalidates the current session generation, clears private-library state, and hides rows without an active user. Older list/save/delete responses cannot repopulate another session. Testing Library covers an already-loaded library disappearing and a delayed prior-session response being ignored. The disposable-PostgreSQL browser journey also checks logout hides private rows while the selected saved set remains as a browser draft. |
| AUD-02 | High | The project-owned team create/delete routes relied only on session cookies; they had no explicit Origin check. Better Auth's auth-route checks do not automatically govern those handlers. This was a missing control, not a reproduced successful exploit. | Both mutations now require an exact origin from `PUBLIC_BASE_URL` or `TRUSTED_ORIGINS`; missing, `null`, malformed, wrong-scheme/port, deceptive, and foreign origins receive 403 before any session or database work. Existing session, ownership, and edge-CIDR checks remain. Origin utility and Fastify injection tests cover allowed and denied requests; the browser journey exercises accepted same-origin mutations against PostgreSQL. |
| AUD-03 | High | Better Auth verification tokens can appear in query strings, and password-reset tokens can appear in the request path. Default Fastify request logs included the raw URL. | The request serializer removes query strings and redacts reset path tokens before logging. Error serializers and the global error path avoid including request input or raw exception details. Unit tests assert that dummy verification and reset tokens do not survive URL sanitization. |
| AUD-04 | High | The Pokédex and damage handlers converted all caught exceptions into 400 responses with `Error.message`. A cache/DB or calculator failure could be misreported as invalid input and expose implementation details. | Known catalog/input problems use `InputValidationError` and retain their clear 400 response. Unexpected exceptions now receive a generic 500 body and a diagnostic log containing a safe error type. Other framework 4xx status codes are preserved with controlled messages. Fastify injection verifies a synthetic exception returns only `{ "error": "Internal server error" }`; damage unknown-name behavior remains covered. |
| AUD-05 | Medium | Helmet's default `img-src 'self' data:` conflicted with the Pokédex image URL returned by PokéAPI; deployed browsers would block the sprite. | Only `img-src` was extended to `https://raw.githubusercontent.com/PokeAPI/sprites/`; Helmet's script policy remains intact. The API response header is tested. The adapter validates fresh and cached sprite URLs against the same HTTPS host/path rule. An Edge/Playwright UI run loaded a stubbed sprite; it did not connect to the deployed site. |
| AUD-06 | Medium | API success responses and status/security metadata were sparse or inaccurate in generated OpenAPI; client types were mostly local TypeScript assertions. | Shared Zod response schemas now describe catalog, chart, Pokédex, damage, curated teams, saved teams, and error bodies. The team POST documents 201, DELETE documents 204/401/403/404 and its id parameter, and all three team operations declare cookie security. Browser calls parse those success payloads at runtime. Fastify tests inspect the generated paths/statuses, and a web unit test rejects a malformed success response. Better Auth's wildcard operations remain library-owned rather than expanded into hand-written individual operation specs. |
| AUD-07 | Medium | A slower detail request could place an old sprite or ID under a newly selected Pokémon name. | Pokédex detail effects abort on selection change and verify the request is still current before accepting a response. A delayed out-of-order Testing Library case proves only the latest details remain visible. |
| AUD-08 | Medium | Damage results remained visible after changing attacker/defender/field inputs, and overlapping/late calculations could overwrite the current matchup. | Each displayed result and error is keyed to the inputs used to calculate it. Old results hide as soon as inputs change; only the latest result for unchanged inputs is accepted. Loading and failure states are visible. Testing Library resolves a calculation after changing the move and asserts the stale result stays hidden. |
| AUD-09 | Medium | Guest keys had no version, writes were unguarded, and the strict submission schema rejected incomplete mid-edit drafts on reload. A storage exception could also interrupt editing. | Draft data has a versioned, permissive edit schema. It migrates the two existing local-storage keys and removes each old key only after storing the new value successfully. Parse/storage errors fall back safely; the UI explains when storage is unavailable. The server/submission schema is unchanged. Unit tests cover migration, incomplete values, malformed data, and blocked storage; a rendered Playwright journey confirms recovery after reload. |
| AUD-10 | Medium | Blank move slots were filtered during each keystroke, moving later moves into earlier fields. | The editor retains all four positions while drafting. Empty slots are compacted only while preparing a team or damage request, where the strict shared input schemas still apply. Component tests and rendered reload checks cover slot stability. |
| AUD-11 | Medium | A failing PostgreSQL cache read happened before the PokéAPI fallback block. A failed cache write could discard successfully fetched details. Old cache data was not labeled as stale. | Cache read/write are best-effort; the adapter can still return fresh upstream fields during a cache outage. Network failure returns validated old descriptive fields with `stale: true`, while unsafe cached sprites are stripped. Adapter tests cover read/write failure, stale fallback, and sprite hosts. A Chien-Pao mapping covers a hyphenated base species that the old conservative rule rejected. |
| AUD-12 | Low | The repository's tests did not previously exercise browser storage migration, error redaction, trusted Origin variants, Pokédex cache failure, session races, or adapter owner filters. | Focused unit/component/API regression tests now cover those boundaries. Four Playwright journeys passed locally for guest reload, chart/build/damage, narrow layout, and the private-team lifecycle. The account journey used two users against disposable PostgreSQL and proved the second user's list was empty and cross-owner deletion returned 404. |
| AUD-13 | Medium | The shared browser request wrapper attached `Content-Type: application/json` even when a DELETE had no body. Fastify rejected the empty JSON body with 400, so the UI could not delete a saved team. | The wrapper adds the JSON header only when a request has a body and no content type was supplied. Unit tests check bodyless DELETE and JSON POST headers; the database-backed browser lifecycle confirms deletion now succeeds. |
| AUD-14 | Low | Playwright's web server waited only for Vite. On a cold start, the page could open before Fastify was ready and return 502 for initial data requests. | Playwright now manages separate API and web processes, waits for `/api/health` as well as the web URL, and uses direct Node entry points so process startup is explicit. The cold-start suite reached all four browser journeys; the final pass used prestarted local servers to avoid this Windows sandbox's child-process shutdown hang. |

## Remaining limits

Docker access to the local engine is denied in this sandbox, but a PostgreSQL service was reachable at `127.0.0.1:5432`. The audit created a dedicated database, applied the migration, ran the browser account journey, and dropped the database afterward. This proves the tested local route/Prisma path for two accounts; CI and production account behavior remain unverified. The exact repo-pinned pnpm version also remains unverified: the installed executable was 12.6.0, and automatic switching to the repo's 11.19.0 failed on a permission-denied AppData lock. Root test scripts passed with automatic switching disabled. The local screenshot preview used stubbed APIs; the database-backed browser journey used the local API.

The API/CSP checks prove the local Fastify response; a Caddy/HTTPS/Tailscale production path and actual deployed response headers were not inspected. Docker image/Compose startup, GitHub protections, current dependency advisories, mail delivery, public product acceptance, and production account access were outside the local evidence collected in this pass. The supported deployment designs and open host checks remain tracked in [requirements](requirements/requirements.md), [security plan](security/security-plan.md), [test strategy](testing/test-strategy.md), and [operations guide](operations.md).

## Recommendations and unresolved product choices

The audit kept its code changes bounded. Consider splitting the growing [main.tsx](../apps/web/src/main.tsx) into feature components and moving route registration out of [app.ts](../apps/api/src/app.ts) as later maintenance work; first agree boundaries and preserve the current behavior with focused tests. Team validation currently uses the damage adapter's catalog validation path, a pragmatic coupling that could be separated if either module grows.

Current feature limits include tab navigation without distinct URLs, a type-only team comparison, no private saved-team update endpoint, no separate persistence for the comparison draft, external sprite hosting, and no account UI for verification or password reset. The requirements still leave the saved-team size policy and public email-verification policy undecided. The pro-team source records also retain the existing Urshifu source-version discrepancy and inconsistent event-date meaning described in the [data-source audit](data-sources.md#audit-of-the-two-current-records). These are recommendations for owner/product review, not additional acceptance criteria introduced by this code audit.
