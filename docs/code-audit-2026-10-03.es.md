# Auditoría del código de la web — 2026-10-03

**Alcance:** interfaz React/Vite, contratos Zod compartidos, rutas y módulos Fastify, límite de propiedad de Prisma, adaptadores de datos y caché, registro de peticiones y seguridad/configuración del repositorio. La [guía de la web](website-guide.es.md) relaciona cada vista con la lógica y los datos que la sustentan. Este informe registra pruebas de código y tests locales; no certifica los ajustes de GitHub, cabeceras HTTP de producción ni el host mini PC.

## Resultado

El sitio tiene un alcance compacto de novena generación y sus principales cálculos del juego usan datos locales fijados de `@smogon/calc`. La auditoría encontró discrepancias en el estado de cuenta, resultados dependientes de entradas, almacenamiento del navegador, gestión de errores de API, contratos de respuesta, sprites/caché de la Pokédex y eliminación de equipos sin cuerpo. Las correcciones siguientes mantienen la pila y el alcance de producto aprobados.

La revisión aplicó la habilidad del repositorio [`react-best-practices`](../.agents/skills/react-best-practices/SKILL.md), incluidas la versión del almacenamiento local y la cancelación de efectos; [`fastify-best-practices`](../.agents/skills/fastify-best-practices/SKILL.md), con esquemas de rutas, errores y pruebas; y [`security-best-practices`](../.agents/skills/security-best-practices/SKILL.md), usando su referencia web de React para el cliente y el plan de seguridad del proyecto para Fastify. Los hallazgos se reprodujeron con Testing Library, pruebas unitarias, inyección de Fastify y un recorrido de navegador con PostgreSQL local desechable. No se usaron el host de producción, credenciales ni fuentes privadas del curso.

La guía de React se aplica a AUD-01 y AUD-07–10: el trabajo asíncrono se vincula a la sesión o las entradas actuales, las modificaciones persistidas tienen una versión explícita y una estructura recuperable, y no se descarta el estado del formulario mientras la persona usuaria lo edita. La guía de Fastify se aplica a AUD-04, AUD-06 y AUD-14: las rutas declaran las respuestas de su propiedad, los códigos de estado siguen siendo significativos, los fallos inesperados se gestionan en el límite del servidor y las pruebas esperan a los servicios que necesitan. La guía de seguridad se aplica a AUD-02, AUD-03 y AUD-05: las mutaciones autenticadas con cookies comprueban su origen, los registros evitan credenciales y las URL de imagen remotas y permisos CSP se restringen cuidadosamente. Son recomendaciones de calidad de código aplicadas al proyecto; no certifican el host desplegado.

Una respuesta lenta también podía llegar después del cambio de usuario. | El cierre/refresco de sesión invalida inmediatamente la generación actual de sesión, borra el estado de la biblioteca privada y oculta sus filas sin un usuario activo. Las respuestas anteriores de listar/guardar/eliminar ya no pueden volver a poblar otra sesión. Era un control ausente, no un exploit reproducido. | Ambas mutaciones exigen ahora un origen exacto incluido en `PUBLIC_BASE_URL` o `TRUSTED_ORIGINS`; valores ausentes, `null`, malformados, con esquema/puerto incorrectos, engañosos o externos reciben 403 antes de consultar sesión o base de datos. La inyección Fastify comprueba que una excepción sintética devuelva solo `{ "error": "Internal server error" }`; el comportamiento de nombre desconocido de daño sigue cubierto. |

Se prueba la cabecera de respuesta de API. El adaptador valida URL de sprites nuevas y en caché con la misma regla de host HTTPS y ruta. Una ejecución de Edge/Playwright cargó un sprite simulado; no conectó con el sitio desplegado. |

## Pruebas realizadas

Después de los cambios pasaron estas comprobaciones locales:

- ESLint en todo el repositorio y comprobación estática de Compose/flujos: se validaron ocho archivos YAML y límites de red seleccionados.
- compilación/comprobación de TypeScript para contratos, web y API; compilación satisfactoria del bundle de producción Vite.
- Vitest: **24 pruebas de API en ocho archivos y 15 pruebas web en cuatro archivos superadas**.
- Playwright: **cuatro recorridos superados** en Microsoft Edge contra la API local y una base PostgreSQL desechable. El recorrido de cuenta cubrió registro, guardar/listar/reabrir/eliminar equipo, cerrar sesión, lista vacía de una segunda cuenta y eliminación entre propietarios con respuesta 404. La base desechable se eliminó al acabar.
- Inyección Fastify: comportamiento de Origin permitido/rechazado, CSP de scripts conservada, respuestas/estados/seguridad OpenAPI generados y respuesta 500 genérica.
- Microsoft Edge mediante Playwright a 1440×960 y 390×844: se renderizaron Overview, emparejamiento de tipos, ID y sprite de Pokédex, borrador y hueco de movimiento tras recargar, resultado de daño y vista de equipos seleccionados. Hubo cero errores de consola/página. Las respuestas de API y bytes del sprite se simularon para mantener aislada la vista local de cuentas/datos externos.

**Navegador:** el complemento Browser no estaba disponible, así que se usó el paquete Playwright instalado y Microsoft Edge del sistema. ## Límites restantes

En este sandbox no se permite acceder al motor Docker local, pero se pudo conectar con PostgreSQL en `127.0.0.1:5432`. La auditoría creó una base específica, aplicó la migración, ejecutó el recorrido de cuenta del navegador y después eliminó esa base. Esto prueba la ruta local y Prisma probada para dos cuentas; el comportamiento de cuenta en CI y producción sigue sin verificar. Tampoco se verificó exactamente la versión de pnpm fijada en el repositorio: el ejecutable instalado era 12.6.0 y el cambio automático a 11.19.0 falló por permiso denegado en un bloqueo de AppData. Los scripts de prueba raíz pasaron con el cambio automático desactivado. La vista local de capturas usó APIs simuladas; el recorrido de navegador con base de datos usó la API local.

Las comprobaciones de API/CSP acreditan la respuesta Fastify local; no se inspeccionaron una ruta de producción Caddy/HTTPS/Tailscale ni las cabeceras reales desplegadas. La puesta en marcha de imagen/Compose Docker, las protecciones GitHub, avisos actuales de dependencias, entrega de correo, aceptación pública del producto y acceso a cuentas de producción quedaron fuera de las pruebas locales recogidas. Los diseños de publicación y verificaciones abiertas del host siguen en [requisitos](requirements/requirements.es.md), [plan de seguridad](security/security-plan.es.md), [estrategia de pruebas](testing/test-strategy.es.md) y [guía de operaciones](operations.es.md).

## Recomendaciones y decisiones de producto pendientes

La auditoría acotó sus cambios de código. Se podría dividir [main.tsx](../apps/web/src/main.tsx) en componentes de función y trasladar el registro de rutas fuera de [app.ts](../apps/api/src/app.ts) como mantenimiento futuro; primero hay que acordar límites y conservar el comportamiento con pruebas específicas. La validación de equipos usa actualmente la ruta de validación de catálogo del adaptador de daño, un acoplamiento pragmático que se podría separar si alguno de los módulos creciese.

Entre los límites actuales de producto están la navegación por pestañas sin URL propia, comparación de equipos solo por tipo, ausencia de endpoint para actualizar un equipo privado guardado, falta de persistencia separada del borrador de comparación, sprites alojados externamente y ausencia de interfaz de cuenta para verificar correo o restablecer contraseña. Los requisitos aún no deciden el tamaño permitido de equipos guardados ni la política pública de verificación de correo. Las fuentes de equipos profesionales también conservan la discrepancia existente sobre la versión de Urshifu y el significado incoherente de las fechas de evento descritos en la [auditoría de fuentes](data-sources.es.md). Son recomendaciones para revisión de producto por la persona propietaria, no nuevos criterios de aceptación introducidos por esta auditoría.
