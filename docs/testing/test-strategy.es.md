# Estrategia de pruebas

**Alcance:** verificación de la versión bilingüe aprobada de la novena generación, su API y el recorrido de staging a producción. Los [requisitos](../requirements/requirements.es.md) definen la aceptación y registran el progreso de implementación; este documento relaciona cada requisito con comprobaciones adecuadas y expone lagunas. El [plan de seguridad](../security/security-plan.es.md) cubre los riesgos y la [guía de operaciones](../operations.es.md), los procedimientos del host. Una prueba local satisfactoria no equivale a aprobar la publicación.

## Qué deben demostrar las comprobaciones

Usa pruebas rápidas para reglas de combate deterministas, contratos y comportamiento de interfaz; pruebas con base de datos para sesiones, propiedad de equipos y caché; recorridos de navegador para flujos de visitantes y cuentas; y comprobaciones en el host para Docker, Caddy, Tailscale, HTTPS, copias de seguridad y promoción. Como la calculadora es una biblioteca externa fijada, las pruebas del proyecto deben centrarse en las entradas, la adaptación y los resultados que promete el producto, en vez de volver a implementar todas sus mecánicas.

La verificación comprueba si el comportamiento implementado satisface los criterios aprobados. La validación del producto también requiere que el propietario revise si la orientación de la tabla, las estadísticas, la comparación, los textos de la calculadora y la atribución de fuentes ayudan a los usuarios a entender los datos. Una prueba de navegador técnicamente correcta no puede emitir ese juicio. No se define un porcentaje global de cobertura arbitrario; los fallos de propiedad, validación, confianza del proxy y recuperación de la publicación necesitan comprobaciones más sólidas que los tipos estáticos o unas pocas constantes.

También pasó `pnpm config:check`: analizó ocho archivos YAML y comprobó algunas restricciones de red de Compose. Son resultados históricos; la evidencia local más reciente aparece a continuación.

El 03-10-2026 pasaron lint, comprobaciones de tipos, compilaciones de producción y `pnpm config:check`; Vitest pasó **24 pruebas API en 8 archivos y 15 pruebas web en 4 archivos**. Otras pruebas cubren `Origin` de confianza exacto, errores inesperados y registros seguros, esquemas/metadatos de seguridad generados, fallback de caché y permisos de sprites de PokéAPI, consultas Prisma limitadas al propietario, cabeceras DELETE sin cuerpo, fallos de migración/almacenamiento de borradores, posiciones fijas de movimientos, carreras de cierre de sesión/sesión, detalles de Pokédex obsoletos y resultados de daño obsoletos. Pasaron los cuatro recorridos Playwright en Microsoft Edge; el de cuenta usó datos PostgreSQL desechables y comprobó el aislamiento entre dos cuentas. El repositorio fija pnpm 11.19.0, pero el ejecutable instalado era 12.6.0; se ejecutaron los scripts sin cambio automático de versión porque pnpm no pudo obtener el bloqueo del almacén en AppData.

El 04-10-2026, el seguimiento de localización pasó lint, comprobaciones de tipos, compilaciones de producción, comprobaciones de configuración y **29 pruebas API en 9 archivos más 37 pruebas web en 9 archivos**. Las regresiones cubren recursos de idioma tipados, fallback y marcadores de posición, selecciones de catálogo traducidas y colisiones, valores canónicos en solicitudes, borradores incompletos y cuatro posiciones de movimientos, búsqueda traducida de Pokédex, mensajes de API/autenticación/validación local por código y resúmenes de daño estructurados. Las pruebas de componentes usan etiquetas sintéticas para ejercer un segundo idioma sin añadir un idioma o selector de producción. Una primera ejecución mostró los tres como correctos, pero se atascó al cerrar los servidores en Windows; al volver a ejecutarlos con servidores gestionados por separado, terminó con código 0. Se usó una URL de base de datos ficticia y no se escribió en ninguna base; no se repitió el recorrido de cuenta/base de datos. Fastify también sirvió los recursos compilados con el CSP esperado y una solicitud HTTP de daño devolvió `matchup` canónico y `hasEffect`. Esto no afirma que se hayan hecho nuevas comprobaciones de Docker, entrada desplegada, caché de base de datos o aceptación en producción.

El 22-10-2026 pasaron ESLint del repositorio, comprobaciones TypeScript de API/web, compilación de contratos, compilación de producción de Vite, auditoría AST de textos de interfaz, **49 pruebas API en 10 archivos y 82 pruebas web en 14 archivos** para la localización, Pokédex, movimientos y rutas directas completados. El [workflow 007](../tfm/ai-methodology/workflows/007-post-rollout-product-evolution.es.md) recoge la evidencia por parte.

## Entornos, datos de prueba y evidencia

- **Local y CI:** usa versiones fijadas de Node/pnpm y una base PostgreSQL desechable para comprobaciones de autenticación y adaptadores Prisma. El workflow CI actual provisiona PostgreSQL 18. Usa cuentas de prueba y equipos sintéticos, nunca credenciales reales ni datos de producción. Reinicia o aísla los registros entre pruebas para que el orden no influya.
- **Datos externos:** simula respuestas y fallos de PokéAPI en pruebas de adaptador. Así se reproducen fallos, caché y comportamiento de formas sin depender de un servicio externo en directo. Revisa manualmente las publicaciones de equipos profesionales: una prueba satisfactoria no demuestra que la fuente sea exacta.
- **Navegador:** ejecuta `pnpm test:e2e` con Docker y la base de datos PostgreSQL local de pruebas disponibles. El runner inicia y cierra los procesos web/API; aplica antes las migraciones pendientes y usa datos desechables. Comprueba resultados después de recargas y entre usuarios, no solo que se haya pulsado un botón o aparezca una página. Conserva trazas o capturas de fallos cuando CI lo permita; una referencia visual sin revisar no demuestra que el contenido sea correcto.
- **Staging y host:** registra el digest y el árbol Git de staging junto a la salida de humo. Para la entrada, guarda resultados esperados y de cabeceras falsificadas, observaciones de redes/puertos Docker y cookies separadas, sin secretos. Para la recuperación, conserva el resultado de restauración y la observación de entrada pública externa con el registro de publicación. La promoción a producción debe referirse al digest probado.

## Preguntas abiertas y límites

El propietario de requisitos aún no ha decidido si los equipos guardados deben tener exactamente seis Pokémon ni si el correo público debe verificarse. Las pruebas relacionadas siguen siendo provisionales. Crear y eliminar equipos de la aplicación ahora exige un `Origin` de confianza exacto; siguen pendientes la entrada desplegada y la verificación CI. También está pendiente la revisión visual y de accesibilidad en ambos idiomas. Las prioridades de requisitos siguen sin decidir; esta estrategia ordena las comprobaciones por riesgo técnico y no asigna prioridad de producto.

No se afirma que exista una prueba de integración de caché PokéAPI respaldada por base de datos, una comprobación completa de cabeceras Caddy/Tailscale ni un ejercicio de reversión. El propietario informa de una restauración de staging, una página pública de producción activa y workflows de staging/producción satisfactorios. El workflow Actions incluye algunas comprobaciones privadas de humo de API en staging, pero no sustituye una comprobación independiente de proxy/seguridad. Actualiza la evidencia de requisitos al pasar nuevas pruebas y deja visibles los fallos.

## Influencia del curso y decisiones del proyecto

**Ingeniería del software → Análisis de requisitos → Validación y verificación de requisitos** informa la distinción entre las comprobaciones de aceptación y la revisión del propietario. **Arquitectura del software → Aplicando Clean Architecture con TypeScript → Testing en Clean Architecture** orienta qué límite protege cada prueba. **Calidad → Testing → E2E asistido por IA** orienta los recorridos críticos en navegador y la revisión de sus pruebas. **Calidad → Métricas, coverage y complejidad → Coverage honesto** advierte de que un porcentaje global alto no sustituye una cobertura basada en riesgos. Son principios del curso; los requisitos, herramientas, pruebas y puertas de publicación concretos son decisiones de Pokémon Tools aprobadas por el propietario o comprobaciones propuestas en relación con ellas.
